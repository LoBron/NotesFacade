# Notes Facade Skill

Этот скилл задает единый порядок работы агента с MCP-фасадом заметок.
Используй его как операционный регламент.

## Обязательные правила

1. Всегда передавай `project_id: "{{PROJECT_ID}}"`, если пользователь не дал другой валидный id.
2. Не придумывай `project_id`. Если id отсутствует или сомнителен, запроси его у пользователя.
3. `title` формулирует агент. Текст пользователя не пересказывается и не переписывается:
   он передается в `capture.text` дословно.
4. Не используй операции, которых нет в MCP-контрактах. Удаление заметок запрещено.
5. Все пути в запросах и ответах должны быть относительными внутри проекта.

## Когда использовать инструменты

- `capture` — создать новую заметку в `00 Inbox` по типу (`thought`, `task`, `project`,
  `reference`) с автозаполнением frontmatter.
- `find` — найти заметки по тексту и, при необходимости, сузить результат фильтрами
  `type` и `status`.
- `read_note` — прочитать заметку целиком или конкретный раздел, получить backlinks и
  outlinks.
- `patch` — точечно изменить frontmatter или фрагмент содержания без полной перезаписи.
- `move_note` — перенести заметку на новый относительный путь с обновлением входящих
  wikilinks.
- `review_queue` — получить кандидатов на регулярный обзор: старый inbox и stale active.
- `validate` — проверить схему frontmatter, дубли id и битые wikilinks в рамках проекта.

## Как вызывать инструменты

### 1) capture

- Выбери `type` из допустимых значений: `thought`, `task`, `project`, `reference`.
- Сформулируй короткий понятный `title`.
- Передай исходный пользовательский текст в `text` без изменений.
- При наличии явных тематических меток добавь `tags`, иначе передай пустой список.

### 2) find

- Для широкого поиска передавай только `query` и `limit`.
- Для уточнения добавляй `type` и/или `status`.
- Если найдено много результатов, предложи уточнить запрос.

### 3) read_note

- Перед чтением убеждайся, что путь относительный и получен из предыдущих ответов.
- Для фокуса на одном блоке передавай `section` с текстом заголовка.
- Используй backlinks/outlinks для навигации по связанным заметкам.

### 4) patch

- Применяй только поддерживаемые операции:
  - `set_field`
  - `remove_field`
  - `append_under_heading`
  - `prepend_under_heading`
  - `replace_block`
- Для `type` и `status` используй только допустимые английские значения схемы.
- Не имитируй полную перезапись заметки через patch.

### 5) move_note

- Передавай только относительные `path` и `new_path` в пределах текущего проекта.
- Используй move для архивирования вместо удаления.
- После move проверяй статус операции и отчет по переписанным ссылкам.

### 6) review_queue

- Запускай по запросу на еженедельный/регулярный обзор заметок.
- Интерпретируй результат как две очереди:
  - `stale_inbox`: заметки в inbox старше порога.
  - `stale_active`: активные заметки без обновления старше порога.

### 7) validate

- Запускай перед крупным ревью заметок или после серии правок.
- Сначала исправляй `errors`, затем `warnings`.
- `info` об осиротевших заметках используй как подсказку для навигации.

## Review-процесс

1. Получи очередь через `review_queue`.
2. Для каждого элемента:
   - прочитай заметку через `read_note`;
   - при необходимости найди связанные материалы через `find`;
   - внеси точечные изменения через `patch` или перемести через `move_note`.
3. После серии изменений запусти `validate`.
4. Сообщи пользователю итог: что изменено, что требует ручного решения, какие риски
   остались.

## Мини-чеклист перед ответом пользователю

- Использован корректный `project_id`.
- `title` сформулирован агентом, `text` в capture передан дословно.
- Не выполнялись запрещенные операции.
- Изменения проверены через `read_note`, `find` или `validate` по ситуации.
